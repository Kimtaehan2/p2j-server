# 미결 사항

**여기 있는 항목은 아직 구현하지 않는다.** 결정이 끝나면 해당 항목을 지우고
결정 문서(`docs/decisions/000N-*.md`)나 명세를 갱신한 뒤 구현한다.

정하지 않은 채로 구현하면, 나중에 바꿀 때 이미 쌓인 데이터를 손봐야 한다.

## A. 명세 자체의 빈틈 (착수 검토에서 발견)

### A-1. Clova STT 를 호출할 서버 엔드포인트가 없다

`02-api-v1.md` 에 STT 관련 엔드포인트가 없다. `/ai/parse` 는 이미 텍스트가 된 발화를 받는다.
`04-backend-v1.md` 는 클로바 연동을 서버 담당(8주차)으로 적어 두었다.

| 선택지 | 내용 | 영향 |
| --- | --- | --- |
| (a) 서버 경유 | 모바일이 오디오를 올리면 서버가 클로바를 호출 | 클로바 키가 서버에만 있다. 업로드 용량·지연 발생 |
| (b) 모바일 온디바이스 | 지금 모바일이 쓰는 `speech_to_text` 유지, 텍스트만 전송 | 서버 작업 없음. 인식 품질이 기기별로 갈리고 `stt_confidence` 근거가 약해짐 |
| (c) 모바일 직접 호출 | 모바일이 클로바를 직접 호출 | **키가 앱에 박힌다. 선택하지 않는다** |

현재 모바일은 (b) 로 동작 중이다. (a) 로 간다면 엔드포인트를 새로 정의해야 한다.

**결정할 것**: 방식 선택. (a) 라면 경로·요청 형식·최대 파일 크기.

### A-2. 04:00 KST 고정과 사용자별 `dayStartHour` 가 충돌한다

`03-erd-v1.md` 의 `users.day_start_hour` 는 기본값 4 인 사용자별 컬럼이다.
그런데 `02-api-v1.md` 와 모바일은 `GET /auth/me` 의 `today` 하나를 전역으로 신뢰한다.

사용자가 값을 바꿀 수 있다면 통계 집계·그룹 랭킹·배치 잡의 "어제"가 사람마다 달라진다.
그룹 스트릭 판정에서 특히 문제가 된다.

| 선택지 | 내용 |
| --- | --- |
| (a) 전역 04:00 고정 | 컬럼은 두되 변경 API 를 만들지 않는다. 그룹 기능이 단순해진다 |
| (b) 사용자별 허용 | 개인 통계만 개인 기준, 그룹 관련은 전부 04:00 고정 |

**결정할 것**: (a) / (b). 지금 구현된 `getServiceDay(now, dayStartHour)` 는 둘 다 지원한다.

### A-3. AI 실패 로그를 위한 `ParseStatus` 가 부족하다

`ParseStatus` 는 `ok` / `partial` / `fallback` 셋이다. 셋 다 "무언가 결과가 나온" 상태다.
LLM 타임아웃, 레이트 리밋, 네트워크 오류처럼 **결과가 아예 없는 실패**를 넣을 값이 없다.

`04-backend-v1.md` 는 "실패한 호출도 남긴다"고 요구하는데, 남길 자리가 없다.

| 선택지 | 내용 |
| --- | --- |
| (a) `error` 값 추가 | `ParseStatus` 에 `error` 를 넣고 `result_json` 은 빈 객체 |
| (b) 별도 컬럼 | `failure_reason` 컬럼을 추가 |

**결정할 것**: 최종보고서의 정확도 근거를 만들려면 실패율이 필요하다. 첫 마이그레이션 전에 정한다.

### A-4. API 예시의 `prs_*`, `chk_*` 와 DB 의 UUID 가 다르다

`02-api-v1.md` 의 예시 응답은 `parse_id: "prs_01H..."`, `check_id: "chk_..."` 같은 접두사 문자열인데,
`03-erd-v1.md` 의 `ai_parses.parse_id` / `load_checks.check_id` 는 `uuid` 타입이다.

| 선택지 | 내용 |
| --- | --- |
| (a) 순수 UUID | 예시를 고친다. DB 그대로 |
| (b) 접두사 유지 | 응답 직렬화 시 `prs_` 를 붙이고 요청에서 떼어낸다 |

**결정할 것**: (a) 가 단순하다. 모바일이 이 값을 문자열로만 다루면 (b) 도 가능하다.

### A-5. `user_daily_stats` 갱신 범위

`todos/{id}/complete` 트랜잭션 안에서 `total_count`, `done_count`, `achievement_rate`,
`total_actual_minutes`, `heavy_done_count`, `streak_count` 를 모두 갱신하기로 되어 있다.

정해지지 않은 것:

- 할 일을 **추가·삭제**할 때 `total_count` 를 즉시 고칠지, 조회 시 다시 셀지
- `defer` 로 날짜가 바뀌면 **양쪽 날짜**의 행을 모두 고칠지
- 과거 날짜의 할 일을 뒤늦게 완료하면 그날 `streak_count` 를 소급할지

소급 처리를 허용하면 스트릭 판정이 배치 잡과 어긋날 수 있다.

**결정할 것**: 갱신 트리거 목록. 즉시 반영 / 배치 중 선택 (기본은 즉시 반영).

### A-6. Todo defer 이력 저장 방식

`todo_items.deferred_from` 은 컬럼 하나라 **직전 1회만** 남는다.
세 번 미룬 할 일은 첫 날짜를 잃는다.

`02-api-v1.md` 의 `/stats/summary` 는 `most_deferred`(가장 많이 미룬 항목)를 요구한다.
컬럼 하나로는 횟수를 셀 수 없다.

| 선택지 | 내용 |
| --- | --- |
| (a) `defer_count` 추가 | 컬럼 하나로 횟수만 센다. 가볍고 `most_deferred` 를 만들 수 있다 |
| (b) 이력 테이블 | `todo_defer_logs` 를 만든다. 정확하지만 테이블이 늘어난다 |

**결정할 것**: (a) 로 충분한지, 최종보고서에 미루기 패턴 분석을 넣을지.

### A-7. API 계약의 원본을 무엇으로 할지

지금 계약이 세 곳에 있다. 서로 어긋나면 무엇이 맞는지 판단할 수 없다.

- `docs/specs/02-api-v1.md` (사람이 쓴 문서)
- 서버가 생성하는 OpenAPI (`/v1/docs-json`)
- Postman Collection (`01-development-plan.md` 가 지정)

| 선택지 | 내용 |
| --- | --- |
| (a) OpenAPI 자동생성이 원본 | 코드와 절대 어긋나지 않는다. 아직 구현되지 않은 엔드포인트는 나오지 않는다 |
| (b) 마크다운 문서가 원본 | 구현 전에 합의할 수 있다. 코드와 어긋날 수 있다 |
| (c) 단계 분리 | 구현 전은 (b), 구현 후는 (a). Postman 은 수동 테스트 용도로만 |

**결정할 것**: (c) 를 쓴다면 "구현 완료" 판정 기준.

## B. 팀 회의에 이미 올라온 항목

`02-api-v1.md` 9절, `03-erd-v1.md`, `04-backend-v1.md` 9절에서 옮겨 왔다.

### B-1. 선언 마감 시각

`DECLARATION_CUTOFF_HOUR` 를 비우면 마감 없음.
11시로 정하면 "아침 선언"이라는 취지가 살지만 늦게 일어난 사람은 참여를 못 한다.

### B-2. 미선언 멤버의 랭킹 처리

0% 로 집계할지 제외할지.
0% 로 하면 압력이 세지고, 제외하면 **선언 자체를 안 하는 게 유리해져** 기능이 무력화된다.

### B-3. 인증샷 보관 기간

Firebase Storage 무료 할당량(5GB)을 고려한다.
30일 후 파일만 삭제하고 `proofs` 행은 남기는 방식이 권장안이다.

### B-4. AI 일일 한도

기본 30회(`AI_PARSE_DAILY_LIMIT`). 팀원 3명 테스트에는 넉넉하지만
시범 사용 기간에는 11월 토큰 예산을 역산해 다시 정해야 한다.

### B-5. 소셜 갱신 방식

폴링(진입 시 + 당겨서 새로고침)으로 시작한다.
WebSocket 은 13주차 이후 여유가 있을 때만 검토한다.

### B-6. 그룹 정원

ERD 의 CHECK 는 3~6명, `groups.max_members` 기본값은 6이다.
2인 그룹을 허용할지 정해야 한다. 허용한다면 CHECK 를 고쳐야 한다.
